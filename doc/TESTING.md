# 测试文档

> 本文档同时记录测试策略与本轮 QA 证据。测试数量随分支持续变化；发布前的权威数字必须来自目标提交上的 `pytest --collect-only -q` 与 `npm run test:e2e -- --list`，不得沿用历史手填数量。

## 1. 测试策略

采用从契约到真实浏览器的多层验证：

| 层级 | 工具 | 范围 | 目的 |
|------|------|------|------|
| **单元测试** | pytest | Store、裁判/适配层、协议、评分、通知、社交、赛制 | 验证底层逻辑与边界 |
| **集成测试** | pytest + TestClient | 鉴权、REST、SSE、WebSocket、生命周期与持久化 | 验证模块协作和错误状态 |
| **架构契约** | pytest 源码扫描 + AST + 导入序 | 游戏注册表、裁判结果鸭子类型、持久化结果唯一 builder、无循环依赖、通用层无游戏分支/静默 game_id 兜底 | 防止解耦架构漂移 |
| **隔离端到端冒烟** | `scripts/e2e_smoke.sh` | 临时 DB/uploads/avatars/logs 下的上传→挑战→赛事；挑战必须 `completed`，且 `result` 具有 `rounds_played`、双数值零和 `deltas` 与有限 `normalized_delta` | 验证核心链路且不写 checkout/主库，`aborted` 不得假通过 |
| **API 关键链路脚本** | `scripts/api_full_test.py` | 挑战精确接收 202 request，校验 opaque `public_id`，轮询到 claim 后再读取 Match；轮询共享 1 秒节拍、校验 HTTP/JSON 并按 `Retry-After` 退避；排行榜同样严格校验 HTTP 200、JSON 对象/对象列表，以 `rated_matches` 验证已有计分样本，并按 `ranking_min_matches` 核对 `ranking_eligible` 与 1-based `rank`，不要求已下架的榜单 `matches_played`；顺序单局 360 秒、双槽争用单局 720 秒，四局并发共享 1440 秒 claim+完成绝对截止，三场循环赛共享 1080 秒截止；并发请求由持久队列自动补槽，不再按 admission 429 客户端重提 | 当前 release 的真实运行与修正复核见 4.1；取消/重试另由 `test_execution_queue` 覆盖，实时 SSE 增量与全部端点仍由其他层覆盖，不把历史结果冒充本轮单次通过 |
| **真浏览器回归** | Playwright + Chromium/Firefox/WebKit | 访客/玩家/组织者/admin 的导航、表单、CRUD、赛事、实时通信 | 用真实 DOM、Console、Network 验证用户行为与跨浏览器差异 |
| **多局/赛事容量脚本** | `scripts/load_test.py` / `contest_stress.py` | 多用户、多游戏、多局终态；load 固定 12 场必须全部接受且全部取得终态，429 耗尽、POST 异常或 waiter 超时均硬失败；draft 名册容量与赛制估算 | 验证所列链路与容量；默认不证明持续打满并发或真实大赛排期 |

## 2. 后端测试范围

配置由 `pyproject.toml` 指定：`testpaths=["bzplat/backend/tests"]`、`pythonpath=["."]`，必须从仓库根运行。测试模块与用例数量会随分支变化；多个独立修复分支汇合后，必须在目标提交重新执行以下命令，不能把任一子分支数字直接相加当成最终证据：

```bash
rg --files bzplat/backend/tests -g 'test_*.py' | wc -l
pytest --collect-only -q
pytest
```

- **闲时策略切换原因**：首次 `idle-only-v1` 对账的 active auto 必须以 `auto_idle_policy_cutover`（“自动排位策略升级后收口”）终结；真实前台入队/重试或赛事 guard 才使用 `auto_yield_foreground`（“自动排位为前台任务让路”）。启动与管理员恢复都须在物理 namespace 清零、launch journal idle、runtime ready 后先提交该策略对账，再执行通用 restart recovery；无回放事件和已有事件两种遗留 auto 都须得到唯一专用终局事件。若 legacy/crash 快照中的 Match 已先 `completed` 或以其他原因 `aborted`，则 Match 真值优先，清除刚贴上的 scheduler marker 后按 completed/interrupted 收口，不能把自然终局倒退为取消。后端终态与前端 neutral 映射均须分别守护。

- **Bot owner 删除线性化**：`test_owner_bot_deletion` 用独立 Store 连接和故障注入守护最终 `BEGIN IMMEDIATE` 边界。删除先提交时，首版隐藏提交后的激活/排位发布、普通版本发布、claim、报名/换 Bot 与 draft 转 live 必须看到 `bot_deleted`/不可用 Bot 并零副作用；首版异常清理还须保留已经提交的墓碑、版本和二进制，通用 hard-delete 不能旁路删除墓碑。竞争写先提交时，删除要么观察到 busy 并整事务零写，要么完整收敛其仍可取消的队列状态，不能留下可重试 interrupted job、queued auto decision、active Local AI lease 或半写墓碑。重复 DELETE 必须继续关闭首个请求提交后尚未关闭的内存 transport，且不改写原 `owner_deleted_at`；客户端在 worker 启动后取消请求也须排空数据库收敛、transport 撤销和唯一一条审计后才传播取消。
- **执行请求与重启恢复**：`test_execution_queue` 须守护 queued 不创建 Match；claim 在同一事务建 Match/index/replay/policy、绑定 pairing 并写 attempt；`starting/running/settling` 都占双资源容量。manual/human/contest 前台在容量充足时可填满 2 match slots / 4 sandbox units，第三条保持 queued；auto 严格后台且至多运行 1 场，不得用第二条 auto 填满双槽。赛事份额 1 只在 manual/human 与 contest 前台间生效，auto 不得被算作“非赛事共享份额”。任一终态与 exact cleanup 只释放本 attempt 容量；非终态 Match 必须保留 settling 与容量。前端 POST/GET 竞态、刷新恢复、source-owned retry，以及 Docker journal/flock/token 精确清理的既有回归继续保留。launch 线性化须组合覆盖两种可能的事务提交顺序：前台（含 human）yield 先提交时，create intent 在同一 `BEGIN IMMEDIATE` 复核 `cancel_requested=0` 失败、Docker RPC 调用数为 0且 journal 保持 idle；launch intent 先提交时，后到 yield 必须保留 creating intent，并由既有真实 yield/cleanup 回归单独证明 exact token/name/label cleanup 后才释放容量。另须直接守护 `settling` 没有新物理启动权，且非 idle host-wide journal 的物理不确定优先于单 job 取消报告。BinaryRunner 还须单独守护 `execution_attempt_not_current` 被转换为 benign `asyncio.CancelledError`，不得升级为 `SandboxControlUncertain` 或触发队列暂停。

- **QA 写隔离**：后端 CLI 在 Store、日志和静态目录创建前校验 DB/端口/运行时目标；前端代理与 Playwright health guard 构成第二、第三道保护。

## 6. 发布门槛

最终验收至少需要：完整 `pytest`、`npm run build`、目标提交静态收集出的全部 Playwright、隔离 `e2e_smoke.sh` 全部通过；同时完成四身份全页面的首屏/中段/页尾截图图片识别，检查浏览器 Console/Network、QA 后端日志、QA 写目标与 50380 服务未被测试触碰。首页最新/热门、History、Bot 详情、搜索与 Cmd+K、MatchViewer、赛事赛程/树、Admin 对局都必须在桌面与移动端截图中逐行识别双方的用户、Bot/真人身份和对局性质；验证长用户名/Bot 名不溢出、移动端序号从 1 开始、性质标签不挤压操作入口，并确认任何缺失身份都不会显示数据库 ID。线上后台任务会合法改变主 DB hash/mtime，此时必须用主日志、实体哨兵与隔离实例标记归因，不能谎称 hash 未变，也不能把正常线上写误判成 QA 污染。若任一项未执行或失败，结论只能是“待验证”，不能写成“已验收”。

三环境发布还必须在隔离实例完成四条真链路：节能沙箱挑战、赛事沙箱对局、本地 Bot 对上传 Bot、本地 Bot 对本地 Bot。逐场核对 execution job 的环境/CPU/内存快照、Docker 实际参数或零 sandbox unit、最终计分原因与回放身份；本地客户端需真实断线重连一次并确认旧 deadline 未延长，旋转令牌后旧连接不能再认证。赛事主机不足一场所需的 4 核/4 GiB 预算时应明确拒绝取得赛事对局，而不是静默降为节能档。

`mobile-public-data-cards.spec.ts` 专门守护 390px 下 Bot 历史与赛事赛程不依赖横向滑动的紧凑卡片：双方身份、owner、轮次、状态与赛果必须默认可见；Bot 历史另显示对局性质，赛事赛程则由所在详情页提供明确的赛事上下文，不重复占用行内空间。主查看入口至少 44px，桌面端仍保留高密度表格；同一组回归还要求反馈附件为中文选择按钮和文件摘要，不再混用浏览器英文原生控件。
