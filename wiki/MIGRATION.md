# 从 Botzone 迁移参赛

本页面向在 Botzone 上已经有程序、准备来本平台参加省赛的选手，只讲迁移要做的事。
平台自身的协议、规则与功能见[通信协议](#/wiki?slug=protocol)、
[Bot 开发指南](#/wiki?slug=bot-dev)与[平台功能指南](#/wiki?slug=guide)。

总路径：注册账号 → 打包上传程序 → 权重放云盘 → 挑战页验证 → 报名省赛。

## 1. 三款游戏的迁移难度

| 游戏 | 兼容度 | 要做的事 |
|------|--------|----------|
| 德州扑克 | 高 | 直接打包上传；注意每场固定 70 手与更长时限下的策略节奏 |
| 点格棋 | 中 | 加一层信封解析，响应套上 `{"response":...}`；多出 `me`/`scores` 字段可用 |
| 五子棋 | 低 | 本平台是三手交换、五手二打、黑方禁手的竞赛规则，动作按阶段输出对象；交互层与开局逻辑需按[五子棋规则](#/wiki?slug=gomoku)重写 |

## 2. 账号与报名

1. 注册账号并完成邮箱验证。
2. 实名赛事在报名时填写姓名、手机号、学校、学号；信息只对赛事组织者与管理员可见。
3. 报名开放期内从赛事详情页派遣自己的 Bot；允许的阶段内可更换，开赛后按赛程快照冻结版本。

## 3. 上传程序

### 路线 A：源码 zip 直传（推荐）

与 Botzone 提交源码的习惯一致，平台在服务端编译运行，本地不需要编译器。

| 项 | 约定 |
|----|------|
| 支持语言 | C、C++、Go、Python 3。Botzone 上的 Java、JavaScript、C#、Pascal 程序需要先改写成这四种语言 |
| 打包 | 整个源码目录打成 zip：不超过 64 MiB、500 个文件，解压后不超过 96 MiB |
| 默认入口 | C 为 `main.c`；C++ 为 `main.cpp` / `main.cc` / `main.cxx`；Go 为 `main.go`；Python 为 zip 根目录的 `__main__.py` 或 `main.py`，与 Botzone 的 Python 打包约定相同。入口不在候选里时，在上传表单显式填写 |
| C/C++ 编译 | `gcc/g++ -O2 -static`，自动定义 `_BOTZONE_ONLINE=1` 与 `BOTARENA_ONLINE=1` |
| C++ 可用库 | nlohmann/json 与 Eigen。Botzone 上的 TensorFlow、libtorch、Boost 等没有，用到就无法直接迁移 |
| Python 可用库 | 仅标准库。依赖 numpy、torch 等第三方库的程序跑不了，需改写为纯标准库，或把重计算部分改为 C/C++ |
| 构建时限 | 服务端编译 120 秒超时 |

### 路线 B：本地编译 ELF 上传

已有构建产物的可以继续上传 Linux x86_64 ELF（不超过 256 MiB）。Windows PE、
macOS Mach-O、ARM64 ELF 与裸 `.py` 都会被拒绝。跨平台构建命令见
[Bot 开发指南](#/wiki?slug=bot-dev)。ELF 路线同样能使用云盘权重。

## 4. 协议对接

平台的交互信封与 Botzone 的 JSON 交互、长时运行约定保持一致：

- Traditional 每个决策点新进程，收到完整历史 `{"requests":[...],"responses":[...]}`，从 `requests[-1]` 取当前决策；
- LongRunning 首回合同上；输出首个响应后立即输出精确握手串 `>>>BOTZONE_REQUEST_KEEP_RUNNING<<<`，之后每回合只收 `{"request":...}`，进程整场保留；
- 响应是单行 `{"response":<动作>}` 并立即 flush，单行不超过 64 KiB；
- Botzone 程序输出的顶层 `data` / `globaldata` 在本平台被忽略：跨回合状态要么每回合重放完整历史重建，要么用 LongRunning 的进程内存；
- 简单交互的程序搬不过来，本平台只有 JSON 信封。在入口加一层「读一行、解析信封、取最后一个请求」的适配即可，决策核心不用动。

### 德州扑克：直接可用

请求的 11 个字段（`num_players`、`dealer_id`、`my_id`、`my_chips`、`my_cards`、
`public_cards`、`history`、`hand`、`max_hand`、`total_win_chips`、`total_win_games`）
与 Botzone 双人德州完全一致；动作码一致：`-1` 弃牌、`-2` 全押、`0` 跟注或过牌、
正数表示本次额外投入的筹码数量。差异只有：每场固定 70 手（Botzone 默认 50），
单步时限 60 秒。更长时限下可以加深搜索与推演。

### 点格棋：加一层信封

棋盘规模一致（6×6 点阵、25 格）。Botzone 每回合给单对象 `{"x","y","pass"}`；
本平台把它放进信封，并在请求里额外提供 `me`（座位）与 `scores`（双方得分）：

```json
{"requests":[{"x":3,"y":4,"pass":0,"me":0,"scores":[1,0]}],"responses":[]}
```

响应从 `{"x":5,"y":4}` 改为 `{"response":{"x":5,"y":4}}`；对手连走收到
`pass:1` 时回 `{"response":{"x":-1,"y":-1}}`。

### 五子棋：规则代差

本平台固定 15×15、26 种指定开局、三手交换、五手二打、黑方禁手；动作按
`phase` 输出分阶段对象（`opening` / `swap` / `move` / `black5_candidates` /
`black5_select` / `pass`），例如 `{"response":{"action":"move","x":4,"y":4}}`。
Botzone 的裸 `x y` 输出会直接协议判负。中盘搜索与估值可以复用，交互层与
开局逻辑按[五子棋规则](#/wiki?slug=gomoku)重写。

## 5. 权重文件与云盘

与 Botzone 的用户存储空间同思路：每账号 256 MB 云盘，在侧边栏「云存储」页管理。
对局开始时把云盘内容以只读快照挂载到 `/mnt/data` 和 `/app/data`；程序里沿用
`data/xxx` 相对路径的习惯即可访问。对局进行中修改云盘不影响已开对局，只影响
之后的对局。单个文件不能超过剩余配额，过大的原始权重先裁剪或量化。

## 6. 上传后验证

1. 上传即触发服务端预检：先用与正式首回合完全相同的信封实测一次通信，
   源码会先编译再预检；协议层问题在这一步就会暴露。
2. 到挑战页实战验证：可以自己两个 Bot 对打，可以选时限，也可以真人亲自上场。
   建议打满几场完整对局，确认完整历史重放与增量状态没有问题。
3. 每款游戏派遣一个排行榜 Bot 即可参与自动排位；日常给同一 Bot 传新版本，
   Rating 会延续。

## 7. 资源与时限

| 项 | Botzone | 本平台 |
|----|---------|--------|
| 沙箱资源 | 1 核 / 256 MB | 日常 1 核 / 512 MB；锦标赛 2 核 / 2 GiB |
| 网络与磁盘 | — | 无网络、只读根文件系统，临时文件写 `/tmp`；状态放内存 |
| 每步时限 | 1 秒（按语言倍率放宽） | 德州单步 60 秒；五子棋每方累计 900/300 秒；点格棋每方累计 900 秒或单步 1 秒 |
| `debug` 输出 | 进公开对局日志 | 终局后限额脱敏，仅授权者可见，不进公开日志 |

## 8. 常见迁移问题

| 症状 | 原因 | 处理 |
|------|------|------|
| 上传后协议错误 | 程序按简单交互读输入，或响应没套 `{"response":...}` | 入口加信封解析层，响应按各游戏格式输出 |
| Python 上传后运行失败 | 用了 numpy、torch 等第三方库 | 运行镜像仅标准库；改纯标准库或换 C/C++ |
| C++ 编译失败 | 用了构建环境没有的库 | 移除依赖，或改用 nlohmann/json、Eigen |
| 跨回合状态丢失 | 依赖 `data` / `globaldata` 回传 | Traditional 每回合重放完整历史；LongRunning 用内存 |
| 五子棋动作被拒 | 输出了旧 `x/y` 格式 | 按阶段输出分阶段动作对象 |
| 源码包被拒 | 超 64 MiB / 500 文件 / 解压 96 MiB，或入口不在包内 | 精简打包，显式填写入口 |
| 权重文件传不上 | 单文件超剩余配额 | 云盘总量 256 MB，先清理或量化压缩 |
| 改了云盘没生效 | 对局开局即快照 | 属预期；改动只影响之后开的对局 |
| 长时运行握手失败 | 握手串缺换行或没 flush | 首响应后单独一行输出精确握手串并 flush |
